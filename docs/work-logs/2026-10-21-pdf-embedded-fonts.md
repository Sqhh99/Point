# 2026-10-21 PDF 嵌入字体选区（fix/pdf-textlayer-embedded-fonts）

- 从 main cc868dd 起分支。样例用 `/workspace/evidence/shared-fixtures/` 中测试员的生成器重新生成，`pdftotext` 输出和测试员的版本一致，只有元数据时间戳不同。
- **选区样式**：按架构设计师的裁定，只作用于 `.pdf-text`，使用 pdf.js 上游的做法（字形透明、整层 0.25、实色 accent），不用 mix-blend-mode。透明度放在整层上，重叠的 span 只合成一次，条纹就没有了。
- **条纹指标**：第一版测得「比选区色深的像素」占 5.6%。看了截图，都是画布字形的抗锯齿边缘：未选中时它们是浅灰（> 235），染色后自然比纯纸面深。改为只统计周围 1px 内都是纯纸面（> 248）的像素后，结果为 0。
- **行间空隙**：
  - span 的行高是 1，多行选区之间会露出页面。渲染后按到下一行的距离设置 `line-height`，再用负的 `margin-top` 抵消，字形位置不动。
  - 只在下一行和这个 span 横向重叠、并且距离 < 1.8 倍字高时才处理（不跨栏、不跨段）。
  - 上标这类小字号 span 会套用同一行最近的正常 span 的行带，否则选区会在上标处留洞。
  - 按行分桶，避免文字很多的页面出现 O(n²) 遍历。
- **段间判断**：e2e 一开始用「两行间距 > 行高 0.9 倍」判断段落间隔，回退到系统 sans-serif 后选区矩形变矮，误判了。改为「行距 > 中位行距 1.3 倍」。
- **字位置偏移（限时探查，未达标）**：
  - 方案 1：把 `content.styles[name].fontFamily` 换成 pdf.js 为画布注册的 FontFace（`g_d0_fN`），文字层用和画布一样的字形。1px 内占比 0.534 / 0.404 / 0.376 / 0.011（100/125/150/200%）。
  - 方案 2：在方案 1 的基础上，用 word-spacing 代替 scaleX 做两端对齐。结果 0.646 / 0.461 / 0.522 / 0.011。
  - 根因：LibreOffice 的 PDF 每行只有一个 text item，字距调整和两端对齐都靠 TJ 数组里的位移完成，pdf.js 的 textContent 不暴露单字位置。另外嵌入字体转换后的字宽和原字体差约 1.2%（306.64 vs 302.98）。200% 时主要是约 3px 的纵向偏差，来自文字层按 PDF 的 ascent 定位、实际字体基线不同。
  - v0.2.3 的方向：从 `page.getOperatorList()` 取出 TJ 的单字位置，按词拆分 span；或者按字体真实的 ascent 修正纵向位置。
  - 两种方案都没有提交（达不到 90%，而且改了字体加载路径，有风险）。
- 行高调整之后，100% 的 1px 内占比从 0.483 降到 0.371。原因是透明字形在更高的行框里有亚像素的位置变化，看不见，只影响这项测量。
- **#72 macOS e2e 失败（spec :132，200% 只测到 92 个单词）**：文字层并没有懒渲染，每档缩放第 1 页都有全部 178 个单词（和 `pdftotext` 一致）。原因是测量只统计完全在视口内的单词，而 macOS runner 窗口高度受屏幕限制（1024×677），200% 时大半页不在视口里。改为滚动取景，直到每个单词都完整出现过一次（也排除了被 sticky 工具栏遮住的顶部）。分母为该页文字层的全部单词。
- 硬断言：
  - 测到的单词数 = 该页文字层单词数；
  - 单词数 ≥ 30（防止空层 0/0 通过）；
  - 四档缩放的 1px 内占比都必须 ≥ 0.20（防回退，同时标 known-issue），实际数值写进 `PDF-EMBEDDED-DRIFT` 行；v0.2.3 把这个下限改回 0.90。
- 结论：选区重影已修复；嵌入字体时字位置偏移是已知问题（实测 1px 内比例 0.26–0.49），v0.2.3 用 operator list 的 TJ 位置文本层修。
