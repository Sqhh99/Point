## 关联
Related to #65（标题栏被裁掉的修复，已合并为 `9857aa1`）。给 UI 设计复核提供 Windows / macOS 上的标题栏截图和数值。

## 改了什么
只加了一个 e2e 用例 `apps/desktop/e2e/titlebar-narrow.spec.ts`，不改产品代码、不改 workflow、不升版本、不动 lockfile。

用例打开一个工作区和一个文件名很长的 PDF，依次把窗口设为：
1. 最小尺寸（读 `BrowserWindow.getMinimumSize()`，当前 900×600）；
2. 1024×700；
3. 最大化。

每种状态：
- 截标题栏和整个窗口：`titlebar-<状态>-<平台>.png`、`window-<状态>-<平台>.png`；
- 测量值写入 `titlebar-<状态>-<平台>.json`：标题栏位置和高度、工作区名和文件名是否被截断、每个按钮的尺寸和是否换行或溢出、窗口按钮相对窗口和屏幕工作区边缘的距离、阅读工具栏是否溢出、`isMaximized`、屏幕工作区；
- 截图和 JSON 用 `testInfo.attach` 附到报告，文件在 `apps/desktop/test-results/<用例目录>/`；
- 每种状态在 CI 日志里打印一行 `TITLEBAR-MEASURE {...}`。

**硬断言**（在 main 上已成立）：标题栏可见、top ≥ 0、bottom ≤ 视口高、高度 36px、标题栏里每个按钮不换行，并且在标题栏和窗口之内。

**只记录、不断言**（main 上不成立，没有跳过任何用例）：
- 最窄宽度和 1024px 下，阅读工具栏溢出（Linux 实测 scrollWidth 368 > clientWidth 241 / 365）；
- 「适合宽度」「框选」换成两行。

这些修好后可以改为硬断言。

## 追加：设计规则断言和截图目录（合并 main `2da2ede` 后）
- 截图和 JSON 写到 `apps/desktop/test-results/screenshots/`，覆盖最小宽度、1024px、最大化三种状态。#67 合入后，CI 每次都会把这个目录上传为 `e2e-screenshots-<os>`。
- 最小宽度下的 UI 设计规则（`expect.soft`，Windows 和 macOS 都跑，不跳过）：
  - (a) 标题栏按钮的文字不换行；
  - (b) 次要按钮先变成纯图标，「打开」最后；「打开」变成纯图标时 ▾ 仍可见；
  - (c) 纯图标按钮 ≥ 32×32，并有 aria-label（「打开」的是「打开」）；
  - (d) 可拖动区域 ≥ 48px，并且不压在 Windows 标题栏按钮区或 macOS 左侧 72px 的红绿灯区上。
- **本 PR 在修复合入之前会保持红。** 第一次 CI（`8d4bc1f`）在 Windows 和 macOS 上都失败在「min: “打开 ▾” wraps」。团队判定这是产品缺陷，断言保持原样，等 功能实现 的修复。

## 追加（第三轮）：标题栏间距、标题栏按钮提示、阅读工具栏布局
三种状态（最小宽度、1024、最大化）在两个平台上都跑，用 `expect.soft`，测量值写进 `titlebar-<状态>-<平台>.json` 的 `layout` 字段。选择器只用 role、aria 和计算出的几何：阅读工具栏是 toolbar「阅读工具」，阅读区是包含它的 `<main>`，对话区是区域「AI 面板」，文档标题是标题栏里显示文件名的那个元素。
- 标题栏：
  - 「打开」在 36px 标题栏里垂直居中，上下间距之差 ≤ 1px；
  - 「打开」右边缘到文档标题左边缘 ≥ 12px（按标题实际绘制的文字位置算）；
  - Windows 和无边框 Linux 的窗口按钮悬停时有提示（title、aria-describedby 或 role=tooltip），文字分别是 最小化 / 最大化或还原 / 关闭。
- 阅读工具栏：
  - 每个子元素和按钮都在工具栏框内；
  - 按钮文字不换行；
  - 页码导航（‹ n / N ›）和缩放百分比始终以文字形式可见；
  - 收起顺序：「框选」先变成纯图标，然后「适合宽度」才收起；收起的项进最右侧的 ⋯ 菜单，菜单第一项是「适合宽度」；所有溢出的按钮都能通过 ⋯ 菜单找到；
  - 纯图标按钮 ≥ 32×32，aria-label 等于原文字，悬停有提示；
  - 阅读区 ≥ 360px，对话区 ≥ 320px，实际宽度都记录下来。最小窗口下如果放不下 360 + 320，也记录（`fits360plus320`）。

## 追加（第四轮）：最小窗口宽度
- 「min」状态不写死 900，而是用 `BrowserWindow.getMinimumSize()` 读窗口真实的最小尺寸，按这个宽度精确调整窗口，读到的值记在 `min-width-<平台>.json`。架构那边会把 minWidth 改成按 侧栏 + 阅读区 360 + 对话区 320 + 分隔条 计算（约 870px）。
- 在最小宽度下断言（`expect.soft`）：
  - 窗口宽度正好等于 getMinimumSize 的宽度；
  - minWidth ≥ 实测的 侧栏 + 360 + 分隔条 + 320 + 对话区右侧剩余；
  - 阅读区 ≥ 360 和对话区 ≥ 320 同时成立；
  - 页面没有横向溢出（`scrollWidth` ≤ 视口宽度），对话区右边缘在窗口内；
  - `setSize(minWidth - 50)` 被拒绝，窗口宽度仍然 ≥ minWidth。
- 本地 Linux 的测量值：minWidth 900，侧栏 240，分隔条 4，需要 924，所以失败；阅读区 256，失败；对话区 400；没有横向溢出；setSize(850) 后宽度仍是 900，通过。

## 追加（第五轮）：分隔条的拖动范围和缩窗后的重新限制
架构决定：minWidth = 侧栏 240 + 阅读区 360 + 分隔条 4 + 对话区 320 = 924，这些值来自共享常量，侧栏不折叠。分隔条的拖动范围用同一组常量限制（阅读区 ≥ 360，对话区 ≥ 320），窗口缩放时还要重新限制。测试里不写死 924，minWidth 照旧从 `getMinimumSize()` 读，侧栏和分隔条宽度按实测值算。
- 拖动：在 1024 和最大化两种状态下，用真实鼠标拖动分隔条。分隔条是阅读区和对话区之间的 role=separator「调整对话面板宽度」，不在阅读工具栏里。向左拖 600px，断言阅读区 ≥ 360；向右拖 600px，断言对话区 ≥ 320；都要求没有横向溢出。每一步都截图。
- 缩窗后重新限制：先最大化（窗口管理器不支持最大化时，比如 xvfb，就铺满工作区），把分隔条拖到一端，再缩到 minWidth，断言阅读区 ≥ 360、对话区 ≥ 320，且没有横向溢出。两个方向都做。
- 持久化：在 localStorage 里找存着当前对话区宽度的 key（实测是 `point.chatWidth`），写入 5000 和 0 两个极端值，重启应用，在 minWidth 下检查同样的限制。如果找不到这样的 key，就记一条说明，只跳过这一小项。如果重启后值没保存下来，就改用重新加载页面，并记录用了哪种方式。
- 结果写在 `splitter-<平台>.json`，截图是 `split-*-<平台>.png`，日志里有一行 `TITLEBAR-SPLITTER`。

## 追加（第六轮）：修正换行判断和记录
- 判断按钮是否换行只看行数：按钮里文字的 client rects 去重后的 top 值个数 ≤ 1。删掉了「文字高度 ≤ 行高 + 1px」这条，它在 Windows/macOS 上把只有一行的 ‹ › − + 和「恢复 100%」误判为失败（系统字体的字形框比计算出的行高高）。文字高度仍然写进 JSON 供参考，但不再断言。「适合宽度」「框选」的「行数 ≤ 1」断言保持不变，在修复合入前继续是红的。
- 改正了第五轮里分隔条位置的写法（它不在阅读工具栏里）。分隔条相关的断言没有改。
